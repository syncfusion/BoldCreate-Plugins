# Stack options

Offer two or three complete stacks that can each deliver the MVP. A stack names the language, the main framework for each component, the data store, the test tool and the hosting target.

## Building the options

1. Know what the team already knows well before you draft any option. If the PRD does not say, ask first. This is the one fact you cannot look up.
2. Add the constraints: stacks the PRD or the user already rules in or out, the platforms the product must run on, and the non-functional needs.
3. Choose options that differ in a way that matters for this product, such as a managed platform against self-hosted, or one language end to end against a separate front end and back end. Two options that differ only in a library name are one option.
4. Check each option against current documentation for licensing and active maintenance. Drop any option whose license does not fit the product or whose main parts are no longer maintained.

## Comparing them

Show one table, then a recommendation in one or two sentences.

| | Option A | Option B | Option C |
|---|---|---|---|
| Stack | | | |
| Team skills | Fit with what the team knows | | |
| Cost | License fees, hosting and running cost at MVP scale | | |
| Hosting | Where it runs and how much the team must operate | | |
| Ecosystem | Libraries, tooling and hiring pool for the must features | | |
| Licensing | License of each main part and any obligation it brings | | |
| Main risk | The one thing most likely to hurt this product | | |

Each cell states a fact or a short judgement with its reason. Avoid scores.

## Recording the choice

The decision record for the stack lists every option from the table, the one chosen, the reason, and the trade-offs accepted.
